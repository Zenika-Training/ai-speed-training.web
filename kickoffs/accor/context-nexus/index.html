Guide d'utilisation · version du 20 novembre 2026

Le Nexus lit.
Vous écrivez.

Ce guide couvre l'utilisation de Context Nexus, sans accès au dépôt de l'outil. Choisissez votre rôle dans les onglets : vous ne verrez que vos procédures, dans l'ordre où vous les ferez. L'onglet Tout le guide suit le cycle du travail, du besoin à la livraison. Pour l'administration, adressez-vous à l'équipe plateforme.

Les nœuds : droits et règles s'héritent

Cinq règles pour tous

  1. Le Nexus lit, vous écrivez.Ce qui part vers Jira ou GitLab part en votre nom, avec votre accord.
  2. Rien sans source.Une information sans source ne compte pas. Une spec draft est une hypothèse non relue : citez-la comme telle.
  3. La machine propose, une personne décide.Aucun verdict de la machine ne remplace une approbation.
  4. Aucun secret ni donnée client.Ni dans un ticket, ni dans une conversation, ni dans un référentiel. Ne cherchez pas à retrouver ce que le Nexus a masqué.
  5. Ne touchez jamais .nexus/ à la main.Un instantané modifié ne donne plus jamais de feu vert.
01

Vue d'ensemble

Tout le cycle d'un coup d'œil : les six phases de haut en bas, une colonne et une couleur par acteur, groupées par famille (produit, ingénierie, gouvernance, exploitation, machine). Entre deux phases, un bandeau marque la gate : sous chaque acteur, une pastille dit s'il la décide, l'approuve ou, pour la machine, l'évalue. Cliquez une étape pour ouvrir sa procédure, une gate pour son détail.

  1. Instantané. Vous recevez de l'équipe plateforme un fichier <dépôt>.nexus.patch. Sur une branche :

    bash
    git switch -c nexus/premier-instantane
    bash
    git apply --index <chemin>/<dépôt>.nexus.patch

    Commitez, poussez, ouvrez la MR, faites-la relire, fusionnez. Le dossier .nexus/ est dans le dépôt.

  2. Tests de caractérisation (si le produit a des specs « as-is ») : vous recevez <dépôt>.patch et un LISEZMOI.md. Même geste (git apply --index), MR, fusion. Votre CI les exécute ; un test rouge signale une spec fausse, pas un bug.

  3. CI. Dans .gitlab-ci.yml, incluez le composant fourni :

    yaml
    include:
  - local: .nexus/ci/gate-check.gitlab-ci.yml

  4. Variable de CI. GitLab › Paramètres › CI/CD › Variables : créez NEXUS_GITLAB_TOKEN, masquée, avec un jeton de projet à portée read_api. Si l'équipe plateforme a mis en place la signature des instantanés, ajoutez aussi (au niveau du groupe) NEXUS_SNAPSHOT_KEYS (la clé publique qu'elle vous donne) et NEXUS_REQUIRE_SIGNATURE=1. NEXUS_FIGMA_TOKEN (jeton Figma de lecture, masqué) est facultatif : sans lui, G2 fait vérifier les maquettes par le central, avec la connexion Figma du produit (P7).

  5. Approbations. Appliquez dans GitLab les règles de .nexus/approvals/rules.yaml et copiez le CODEOWNERS de .nexus/approvals/ à la racine. Ils viennent des responsables de gate nommés au central (P16).

  6. Commandes Claude Code. Demandez à l'équipe plateforme les fichiers .mcp.json, .claude/commands/ et .claude/skills/ de votre dépôt (elle les génère pour vous). Commitez-les par MR : toute l'équipe en profite, et personne n'a besoin du dépôt de l'outil.

Équiper son poste et Claude Code

DéveloppeurQATech Leadétapes 1–4 : une fois par posteétapes 5–8 : une fois par dépôt
Avant de commencerIl vous faut : Claude Code installé (méthode de l'organisation), git, uv, le clone du dépôt d'équipe sur la branche avec .nexus/ et le .mcp.json commité par le Tech Lead (P2), Zscaler actif pour GitLab, vos comptes Jira et GitLab, et votre rôle contributeur sur le produit (P1). Aucun jeton du central n'est à demander ni à recopier : Claude Code se connecte au central avec votre compte de l'organisation (étape 7).

  1. Installer nexus-local, le serveur qui lit l'instantané sur votre poste. Ouvrez la page Installer son poste du central (menu de la webapp › Installer mon poste, ou https://<adresse du central>/api/v1/poste), connectez-vous, téléchargez le paquet, vérifiez son empreinte SHA-256, puis installez le fichier avec la commande uv tool install affichée sur la page.

    Si le navigateur a ajouté (1), rendez au fichier son nom d'origine avant de l'installer. La page indique comment configurer les certificats, le miroir PyPI et Python derrière Zscaler.

    Vérifiez que nexus-local --help répond.

  2. Votre jeton GitLab personnel (portée read_api), pour que Claude lise la CI de vos MR. Créez-le vous-même dans GitLab (Préférences › Jetons d'accès) et rangez-le dans ~/.config/nexus-local/.env, hors de tout dépôt. Créez le fichier avec les permissions 600 comme indiqué sur la page, puis saisissez cette ligne dans un éditeur :

    .env
    SPECKIT_GITLAB_TOKEN=<votre jeton personnel GitLab>

  3. Clé de signature (si l'équipe plateforme en publie une) : collez la ligne de clé publique dans ~/.config/nexus-local/snapshot-keys. C'est une clé publique, pas un secret.

  4. Brancher Jira et GitLab dans Claude Code. Ajoutez les serveurs MCP Jira et GitLab de l'organisation au niveau utilisateur avec les commandes publiées sur Installer son poste. Si une commande manque, demandez-la à la plateforme. Authentifiez chaque serveur depuis /mcp si Claude Code le demande. Sans MCP GitLab, la livraison peut passer par git push et glab.

    Sans accès au MCP Jira (non fourni, ou vous n'avez pas les droits), Claude lit et écrit dans Jira par l'API REST, avec votre jeton, au travers de nexus-local.

    Repli REST de Jira (facultatif, à poser si le MCP Jira vous manque). Dans le même fichier ~/.config/nexus-local/.env, hors de tout dépôt :

    .env
    SPECKIT_JIRA_URL=https://<votre-site>.atlassian.net
SPECKIT_JIRA_EMAIL=<votre e-mail Atlassian>
SPECKIT_JIRA_TOKEN=<votre jeton d'API Atlassian>

    Le jeton se crée sur id.atlassian.com (Sécurité › Jetons d'API). Pour un Jira Data Center, omettez SPECKIT_JIRA_EMAIL et mettez un jeton d'accès personnel. Vérifiez : nexus-local jira access doit répondre "reachable": true avec votre nom. Les collectes Atlassian se font sans Zscaler.

    Les droits sont les vôtres : Claude ne voit et n'écrit que ce que vous pouvez voir et écrire. Claude utilise le MCP Jira quand il est là ; le repli prend le relais quand il est absent ou non authentifié. L'écriture reste celle de /deliver : un commentaire et une transition, après un aperçu que vous validez.

    MCP Figmafigma (le MCP Figma officiel) n'est posé que si le produit a un design system qui fait foi (P7) : authentifiez-le par /mcp › figma › Authenticate, avec votre compte Figma. Claude y lit le design system et les maquettes ; ses outils d'écriture sont refusés dans .claude/settings.json.

    Faites de même une fois dans un terminal, pour les commandes de nexus-local qui parlent au central (la section « Existant ailleurs » du brief, snapshot pull) :

    bash
    nexus-local --repo . login

    Le navigateur s'ouvre de la même façon. Pour couper l'accès de ce poste : nexus-local --repo . logout.

    Poste en conteneur, voie recommandée : la page « Installer mon poste » du central (onglet « Conteneur Docker ») fournit le kit à télécharger (nexus-poste-kit.zip : Dockerfile, compose, wheel et adresse du central), que vous construisez sur votre machine ; aucune image n'est publiée (sources : deploy/poste/, voir son README.md). L'image fixe donc les ports de retour : NEXUS_LOCAL_CALLBACK_PORT (port de nexus-local login) et NEXUS_LOCAL_CALLBACK_HOST=0.0.0.0 (adresse d'écoute dans le conteneur), MCP_OAUTH_CALLBACK_PORT pour Claude Code. Derrière Zscaler, le conteneur lit en lecture seule le certificat déjà présent sur votre poste (NEXUS_CA_FILE et compose.ca.yaml) : il n'entre ni dans l'image ni dans le dépôt.

Modifier ou désactiver une règle héritée

Une exception : un approbateur nommé et une date de fin (6 mois au plus, 3 pour un produit de criticité haute).

Critère ajouté ou rendu bloquant

Avertit pendant 30 jours avant de bloquer, sauf urgence motivée.

Ajouter ou ajuster un contrôle de code

  1. Règles › Contrôles, famille contrôles de code, niveau de votre produit.

  2. Lisez la valeur effective et le niveau d'où elle vient.

  3. Ajoutez le contrôle (par exemple la commande de tests de votre pile), ou, pour un contrôle hérité, renseignez l'approbateur de l'exception.

  4. Enregistrez. Les autres familles se règlent de même : contrôles du ticket, lecture de la CI, mise à jour du ticket, files de travail (les vues de /tickets).

Ajouter un critère à une gate

  1. Rédigez-le d'abord avec la fiche de critère.

  2. Règles › Quality gates, choisissez le niveau et la gate.

  3. Ajoutez le critère : méthode (contrôle automatique, juge, humain), bloquant ou avertissement, action en cas de refus, rôle à engager. Réglez le chemin d'approbation par criticité si besoin.

  4. Enregistrez : la date « en vigueur le … » s'affiche.

  5. Une exception datée se suit dans l'onglet Exceptions, celles qui échoient d'abord.

Bon à savoirÉcrire une règle en français ne crée pas un contrôle : demandez à l'équipe plateforme si un contrôle existant la couvre. Aujourd'hui, G3 est évaluée par la machine ; G2 l'est en partie, sur une MR qui modifie une spec (contrôles déterministes, dont les maquettes Figma ; pour les critères confiés au juge, la forme est contrôlée d'abord : mal formée, le critère échoue ou reste non évaluable ; bien formée et juge désactivé, il passe « en attente humaine », le fond restant à relire, jamais un GO par défaut) ; G1 donne un avis sur le poste (/gate g1 <clé>), sans rien consigner au central ; G4, G5 et G6 sont définies mais pas évaluées.

En-tête de spec

Toute première ligne de spec.md. Versions exactes seulement (jamais une plage ni latest) ; la cible d'une exigence est un nombre, l'unité à part. Retirez les listes vides.

yaml
---
capacites: [CAP-003]                # capacités concernées
tickets: [ABC-123]                  # origine des critères d'acceptation
components:                         # composants réutilisés, version exacte
  - {name: "paiement-sdk", version: "4.2.1"}
designs:                            # maquettes figées : lien Figma avec node-id, version
  - {url: "https://www.figma.com/design/<clé>/<titre>?node-id=12-34", version: "1234567890"}
contracts:                          # contrats d'API, chemins dans le dépôt
  - {kind: openapi, path: contracts/paiement/lien.yaml}
nfr:                                # exigences non fonctionnelles chiffrées
  - {id: NFR-01, metric: latence-p95, target: 300, unit: ms}
---

Une maquette hors Figma reste « en attente » tant que l'UX ne l'a pas confirmée. Dans le corps, pour chaque scénario : « Critères d'acceptation (report du ticket ABC-123 le <date>) » puis CA-01 : Étant donné …, quand …, alors ….

Vocabulaire

Nœud

Organisation, regroupement ou produit ; règles et droits s'y attachent et s'héritent.

Central

Le service partagé : webapp, serveur nexus, registre.

Instantané (.nexus/)

La copie signée des règles et du contexte d'un produit, dans son dépôt.

Brief

Le contexte assemblé pour un ticket : règles, capacité, extraits sourcés, avertissements.

Spec as-is

La description sourcée de ce que fait déjà une capacité.

Question ouverte

Une incertitude d'une spec, à trancher par une personne.

Contrôles du ticket

Ce qui juge un ticket prêt.

Contrôles de code

Tests, lint, secrets, spec à jour, jetons du design system, lancés sur le poste.

Quality gate

G1 à G6 seulement : le passage d'une phase à la suivante, décidé par une personne.

Passage

Une évaluation d'une gate sur une MR ou un ticket, à un commit donné.

Design system qui fait foi

La bibliothèque Figma désignée pour un nœud ; ses jetons partent dans l'instantané.

Exception

Une règle héritée modifiée, avec approbateur et date de fin.

Dérogation

Un critère bloquant en échec couvert par le Decision Guarantor, jusqu'à une date.
