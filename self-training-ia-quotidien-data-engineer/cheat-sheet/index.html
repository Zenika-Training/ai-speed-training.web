Un agent de code sur ton pipeline

L'agent fait le mécanique : requêtes, profilage, code, tests. Les hypothèses, le grain, les décisions et la preuve : c'est toi.

Atelier Data Engineerà retenir, module par module

  • Run en échec : des hypothèses et leurs vérifications avant toute correction. L'erreur s'affiche en aval, elle naît souvent à la source.
  • Nouvelle source : profiler avant de modéliser. Unités, fuseaux, doublons, grain prouvé par un comptage.
  • Modèle : le grain écrit en toutes lettres, choisi par toi, en mode plan.
  • Jointure : corriger le grain, pas maquiller le calcul ; un test unitaire le prouve.
  • Tests de données : chaque échec appelle une décision, pas un test affaibli.
  • Chargement : relancer ne change pas le résultat, et on le prouve en relançant.
  • CI : une revue avant une réécriture ; un secret commité se révoque.
  • Passation : une doc qui dit ce que le code ne dit pas ; un runbook qui dit quoi faire.

Dès demain

  • Au prochain run en échec, demande des hypothèses et leurs vérifications avant d'autoriser la moindre modification.
  • Avant chaque nouveau modèle, écris son grain (« une ligne par… »).

Ce que l'agent fait pour toi

  • Remonter le lignage d'une erreur jusqu'au fichier source.
  • Profiler une source en quelques requêtes.
  • Proposer des options de modèle, des tests, une stratégie de reprise.
  • Rejouer un scénario et compter les lignes pour prouver.
  • Relire une CI, documenter, rédiger un runbook.

Avant de donner une vraie donnée

  1. Quelle sensibilité ? La classification des données de ton entreprise s'applique.
  2. Ai-je besoin des lignes ? Le schéma ou un agrégat suffit le plus souvent.
  3. Suis-je dans l'outil autorisé ? Et l'agent a-t-il seulement les accès nécessaires ?

Ce qui reste ta décision

  • La cause retenue et la correction ; qui prévenir à la source.
  • Le grain et la définition d'un indicateur.
  • Le traitement d'un test en échec, et la stratégie de reprise.
  • Ce qui part en production, et quand.

Les 5 réflexes avec un agent sur un pipeline

  1. Lecture seule d'abord : comprendre avant de modifier.
  2. Une preuve par affirmation : une requête, un comptage, un test.
  3. Le grain écrit avant le code.
  4. Le diff relu, limité à ce qui était demandé.
  5. Décide toi-même : l'agent propose, tu choisis.

Prompts types et pièges

Comprendre avant de corriger, prouver avant de livrer.

Prompts typesune session neuve par tâche, en lecture seule tant que tu n'as pas compris

Diagnostiquer un run
Tâche :où l'erreur apparaît, où elle naît ; 2-3 hypothèses avec leur vérification ; fais-les.
Règles :ne modifie aucun fichier.
Profiler une source
Tâche :par colonne : type, vides, distincts, min, max ; la clé ; les pièges.
Format :un tableau, puis chaque piège avec sa requête.
Corriger et prouver
Tâche :corrige <modèle> sans écarter de ligne.
Preuve :lignes et vides par source, avant / après ; le test passe.
Relire une CI
Tâche :revue en lecture seule : ligne, risque pour ce projet, correction, gravité.
Format :du plus grave au moins grave.

Pièges vus dans l'atelier

  • Une source qui change de format de date sans prévenir.
  • Des montants en centimes, des horodatages en UTC.
  • Une jointure qui multiplie les lignes et gonfle un taux.
  • Un enregistrement renvoyé deux fois, un hôtel de recette en production.
  • Un chargement en ajout qui double à chaque relance.

Avant d'accepter une modification

1. Le diff est limitéTouche-t-il seulement ce que j'ai demandé ?
2. La preuve existeQuelle requête, quel test le montre ?
3. Rien n'est affaibliUn test retiré, une ligne écartée, un avertissement ?

Mots-clésglossaire complet sur le site

Grain ce que représente une ligne d'une table : « une ligne par séjour ».
Idempotence relancer un traitement donne le même résultat, sans doublons.
Lignage le chemin d'une donnée, de la source au tableau de bord.
Test de données une règle vérifiée sur les données à chaque construction.
Test unitaire des entrées écrites à la main, une sortie attendue : il vérifie le code.
Context window tout ce que le modèle « voit » au moment de répondre.
