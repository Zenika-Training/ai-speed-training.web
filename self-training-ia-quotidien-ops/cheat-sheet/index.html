Un agent de code sur ton exploitation

L'agent lit, résume et propose : logs, manifestes, plans, messages. Les hypothèses, les décisions et l'action en production : c'est toi.

Atelier Opsà retenir, module par module

  • Déploiement : les risques d'abord, puis un plan où chaque étape a son contrôle et son retour arrière ; ce qui ferme la porte (supprimer une colonne) part à part.
  • Signaux : faire écrire les commandes qui résument les logs, pas les logs collés ; le bruit est constant, le signal suit un événement.
  • Alertes : mesurer ce que chaque alerte a apporté avant de couper ; on ne réveille que pour un symptôme ou un risque de perte.
  • Incident : le début se lit dans les métriques ; des hypothèses vérifiées avant d'agir ; une action réversible, décidée par toi.
  • Scripts : relus avant d'être lancés ; un mode à blanc par défaut dans tout ce qui supprime.
  • IaC et CI : une revue avant une réécriture ; un secret exposé se change.
  • Retour d'expérience : des faits sourcés, sans blâme, trois actions suivies au plus.

Dès demain

  • Au prochain déploiement, demande jusqu'à quelle étape le retour arrière reste possible.
  • Au prochain incident, trois hypothèses et leurs vérifications avant la première action.

Ce que l'agent fait pour toi

  • Croiser une release, une migration, une configuration et la volumétrie.
  • Résumer 20 000 lignes de logs avec grep, awk, sort, uniq.
  • Compter un mois d'alertes, calculer un impact.
  • Relire un script, des manifestes, une CI, sans rien lancer.
  • Rédiger un plan, un message de statut, un post-mortem.

Avant de donner une vraie donnée

  1. Jamais de secret : mot de passe, jeton, kubeconfig.
  2. Des logs filtrés ou un agrégat : les logs bruts contiennent souvent des données personnelles.
  3. Suis-je dans l'outil autorisé ? Et l'agent a-t-il seulement les accès nécessaires ?

Ce qui reste ta décision

  • Le go / no-go d'un déploiement, et ses conditions.
  • Qui on réveille la nuit, et pour quoi.
  • L'action en production pendant un incident, et qui prévenir avant.
  • Ce qu'on corrige maintenant, ce qui devient un ticket.

Les 5 réflexes avec un agent en exploitation

  1. Lecture seule d'abord : comprendre avant d'agir.
  2. Un fait daté par affirmation : une ligne, une métrique, une commande.
  3. Le retour arrière prévu avant le changement.
  4. Chaque demande d'accord lue : la commande, le chemin, l'option.
  5. Décide toi-même : l'agent propose, tu lances.

Prompts types et pièges

Comprendre avant d'agir, prévoir le retour arrière, décider soi-même.

Prompts typesune session neuve par tâche, en lecture seule tant que tu n'as pas compris

Relire un déploiement
Tâche :chaque risque : ce qui casse, quand, ce que voient les utilisateurs, comment le détecter.
Règles :une ligne de fichier par risque ; ne modifie rien.
Résumer des logs
Tâche :répartition par niveau, par message, par heure ; le signal et ce qui le précède.
Règles :ne lis pas le fichier en entier ; montre chaque commande.
Diagnostiquer un incident
Tâche :l'heure de début d'après les métriques ; 3 hypothèses, une vérification chacune ; fais-les.
Règles :lecture seule ; aucune action proposée.
Écrire un script qui supprime
Tâche :mode à blanc par défaut, --appliquer pour agir, set -euo pipefail, guillemets.
Règles :montre-le avant de l'exécuter.

Pièges vus dans l'atelier

  • Une migration qui supprime une colonne pendant qu'un rolling update fait tourner l'ancienne version.
  • Une alerte sur chaque erreur, acquittée par réflexe le jour où elle compte.
  • Un CronJob sans fuseau : 07:45 UTC, c'est 08:45 à Paris.
  • Le dernier déploiement accusé sur une coïncidence.
  • cd $1 && rm -rf * lancé sans argument.
  • Un mot de passe dans une ConfigMap, un kubeconfig affiché dans la CI.

Avant d'accepter une action

1. Je sais ce qu'elle faitQuelle commande, sur quel chemin, avec quelle option ?
2. Elle est réversibleComment je reviens en arrière si c'est faux ?
3. Elle repose sur un faitQuelle ligne, quelle métrique le montre ?

Mots-clésglossaire complet sur le site

SLO l'objectif fixé sur ce que voit l'utilisateur : 99,5 % de scans en succès sur 30 jours.
Budget d'erreur ce que le SLO autorise à échouer ; on alerte quand il se consomme vite.
Expand / contract ajouter le nouveau, faire cohabiter, supprimer l'ancien plus tard.
Mode à blanc le script affiche ce qu'il ferait, sans le faire.
Post-mortem sans blâme ce qui, dans le système, a permis l'incident.
Context window tout ce que le modèle « voit » au moment de répondre.
