Harness et orchestrateurs ​

Le harness fait tourner un agent pendant une session de travail, avec vous ; l’orchestrateur fait tourner un processus conçu par vous, qui survit à la session. Cette fiche détaille l’anatomie d’un harness et son marché, ce qu’un harness sait déjà orchestrer, la frontière avec un orchestrateur, quatre patterns multi-agents, le marché des orchestrateurs et le SDD.

Ordres de grandeur : le marché bouge très vite (renommages, rachats). Les listes ci-dessous donnent des familles, pas un classement.

Anatomie d’un harness ​

Partie 4 · slide « Anatomie d’un harness »

Agent de code = modèle + harness. Le harness est tout le code, la configuration et la logique d’exécution qui ne sont pas le modèle (définition reprise de LangChain, « The Anatomy of an Agent Harness »).

Même modèle, deux harness : des résultats et des coûts très différents (ordre de grandeur des comparatifs de 2026, pas un benchmark de référence). Le harness est un levier de performance au même titre que le choix du modèle.

ComposantCe qu’il fait
Boucletours, arrêt, reprise, gestion d’erreurs
Outils intégrésfichiers, shell, recherche, web, MCP
Contexteassemblage, compaction, cache, mémoire
Permissionsallow / ask / deny, sandbox, conteneur
Hooksscripts déterministes avant / après chaque action
Sous-agentsdéléguer avec un contexte isolé
Observabilitétraces, coût par session, rejouer les décisions
Extensionsskills, commandes, plugins, instructions projet (AGENTS.md)

Les hooks sont déterministes : un hook qui lance le linter après chaque modification ne dépend pas de la bonne volonté du modèle. C’est le premier guardrail côté poste.

Critères de choix :

  • lock-in modèle (un seul fournisseur ou plusieurs) ;
  • finesse des permissions et sandbox ;
  • gestion du contexte ;
  • extensibilité (skills, hooks, MCP) ;
  • possibilité de passer par la gateway de l’entreprise ;
  • licence.

Orchestrer depuis le harness ​

Partie 4 · slide « Orchestrer depuis le harness »

Un harness sait déjà faire travailler plusieurs agents : c’est le modèle qui décide, pendant la session.

MécanismeCe qu’il fait
Sous-agentsl’agent principal délègue une sous-tâche à un agent au contexte vierge, et n’en récupère qu’un résumé
Agents en parallèleplusieurs sessions sur plusieurs tâches, chacune dans son worktree git, puis on fusionne
Mode headlessle harness sans interface, lancé par une commande (claude -p, codex exec, copilot -p) depuis un script ou la CI

La limite : tout vit dans la session. Le modèle décide du découpage au fil de l’eau, et l’état est dans le contexte : si la session tombe (crash, quota, machine éteinte), le travail en cours est perdu, et rien ne garantit que deux exécutions suivent le même chemin.

Pour un développeur devant sa tâche, cela suffit très souvent.

Harness ou orchestrateur ? ​

Partie 4 · slides « Le harness : une session de travail » et « L’orchestrateur : un processus conçu par vous »

Le harness fait tourner un agent dans une session ; l’orchestrateur fait tourner un processus, qui survit à la session.

HarnessOrchestrateur
Qui trace le cheminle modèle, pendant la sessionvous, dans un processus écrit à l’avance
Déclenché parvous, au clavierun événement : ticket, webhook, planning
Étatdans le contextesauvegardé à chaque étape
Si ça planteon relance la sessionreprise à l’étape en échec
Échellequelques agentsdes centaines de tâches

Ce qu’apporte un orchestrateur, ce n’est pas plus d’intelligence, ce sont des garanties d’exploitation :

  • durabilité : une tâche de plusieurs heures reprend après un crash, un quota ou un redémarrage ;
  • prévisibilité : le chemin est écrit, donc testable et rejouable ; une validation humaine est une vraie étape du processus, pas une consigne dans un prompt ;
  • autonomie : le processus tourne sans personne au clavier, déclenché par un événement ;
  • pilotage : traces, coût et taux d’échec par étape ; un modèle différent selon l’étape ;
  • produit : un agent de support client ou un pipeline de documents ne vit pas dans un terminal.

Quand passer à l’orchestrateur ? Quand le travail devient un processus répété, sans surveillance, long ou critique.

Le plus souvent, on combine les deux : l’orchestrateur appelle des harness comme exécutants. C’est l’exemple de la slide : un ticket créé déclenche le processus ; un agent analyse, un harness en mode headless code, un agent juge vérifie, un humain valide avant la PR. Si l’agent juge tombe en panne, l’orchestrateur reprend à cette étape avec l’état des étapes précédentes. Dans l’analogie de la flotte, le harness est le véhicule équipé ; l’orchestrateur est le centre de dispatch qui planifie les tournées, suit chaque livraison et réaffecte le colis si une camionnette tombe en panne.

Quatre patterns d’orchestration ​

Partie 4 · slide « Quatre patterns d’orchestration »

Chaque pattern répond à une limite d’un agent seul : il se relit mal, il a ses biais, il ne sait pas tout, il ne peut pas tout tenir en contexte. Ils se montent depuis un harness (sous-agents) comme dans un orchestrateur (graphe) : ce qui change, c’est qui décide de l’enchaînement et ce qui survit à une panne.

PatternPrincipeExemple
Agent jugeun agent outillé vérifie le travail d’un autre : il lance les tests, lit le diff, puis tranchebarrière avant la revue humaine ; évaluer d’autres agents
Adversarialun agent cherche la faille, l’autre défend ; un arbitre tranche (variante : le débat)red team : un agent écrit des tests pour casser le code, l’autre corrige
Handoffl’agent courant passe la main, avec la conversation et le contexte, à un spécialistesupport : triage → facturation (OpenAI Agents SDK, Google ADK)
Hiérarchiqueun orchestrateur d’orchestrateurs : un lead délègue à des chefs d’équipe, qui délèguent à des workersune équipe d’agents par domaine (CrewAI, LangGraph)
  • Agent juge ou simple relecteur ? Le relecteur (LLM-as-a-judge) lit du texte et commente ; le juge (Agent-as-a-Judge, Zhuge et al., 2024) vérifie en agissant et rend un verdict. C’est la parade au « faux succès » de la fiche 3.
  • Pourquoi un adversaire ? Un agent se relit mal lui-même ; un adversaire n’a pas le même biais. Le prix : deux à trois fois plus d’appels.
  • Handoff ou routeur ? Un routeur aiguille une fois, à l’entrée ; avec le handoff, chaque agent peut passer la main en cours de route, sans chef central.

On entend aussi parler de tableau noir (blackboard : les agents lisent et écrivent un état partagé), d’humain dans la boucle (une étape de validation dans le graphe) ou d’essaim : ce sont des combinaisons de ces briques.

Le marché des orchestrateurs ​

Partie 4 · slide « Le marché des orchestrateurs »

FamilleCe qu’elle apporteExemples
Frameworks d’agents (code) : on décrit le grapheLangGraph (graphe d’états, reprise, humain dans la boucle), CrewAI (équipes de rôles), Microsoft Agent Framework (successeur d’AutoGen et Semantic Kernel, annoncé en octobre 2025), Google ADK, OpenAI Agents SDK (handoffs), LlamaIndex, Mastra (TypeScript)

On n’a pas besoin d’un framework d’orchestration pour commencer. Pour un usage développeur, l’orchestration intégrée au harness suffit souvent (voir Orchestrer depuis le harness). Les frameworks deviennent utiles quand on construit un produit agentique (agent de support client, pipeline de traitement de documents) ou quand on a besoin de garanties de reprise.

Temporal est un moteur de workflows généraliste, pas spécifique à l’IA : on l’utilise de plus en plus pour les agents, car une tâche d’agent longue rencontre forcément des pannes réseau, des quotas, des redémarrages.

Et le SDD dans tout ça ? ​

Partie 4 · slide « Et le SDD dans tout ça ? »

ÉtapeContenuArtefact
1. Spécifierle quoi et le pourquoi, relu par un humainspec.md
2. Planifierle comment techniqueplan.md
3. Découperde petites tâches vérifiablestasks.md
4. Implémenterun agent (ou des workers) par tâchecode + tests

Le SDD est un orchestrateur préconfiguré basé sur les specs : une chaîne déjà câblée, dont chaque sortie est un fichier versionné relu par un humain.

Les principes du SDD face à un orchestrateur :

OrchestrateurSDD
Le chemindu code : un graphe que vous écrivezune méthode : spec → plan → tâches → code, toujours la même
L’étatsauvegardé dans le moteurdans des fichiers versionnés, relisibles par tous
La validationune étape d’approbation dans le graphechaque étape relue par un humain avant la suivante
Le déclencheurun événement, sans surveillancevous, dans votre harness
  • La spec est la source de vérité : on corrige la spec, pas le code généré.
  • Reprendre, c’est relire les fichiers : dans n’importe quelle session et n’importe quel harness.
  • Les deux se combinent : un orchestrateur peut lancer les tâches d’un tasks.md.

Avec un orchestrateur comme LangGraph, vous décrivez le graphe ; avec le SDD, le graphe est fourni (spec → plan → tâches → code). Il donne aux agents un objectif écrit et un critère d’arrêt, ce qui manquait dans les modes d’échec de la fiche 3 (dérive de contexte, faux succès). Le SDD produit le plan, le fait valider par un humain, puis l’exécute.
