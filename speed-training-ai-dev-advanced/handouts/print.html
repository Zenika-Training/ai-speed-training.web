Sous le capot

Pourquoi un agent coûte cher, est lent ou se trompe : cette fiche reprend l’ouverture et le module 1 dans l’ordre des slides, de la boucle agentique jusqu’à la facture d’une session.

Vibe coding vs AI-driven dev

Ouverture · slide « Vibe coding vs AI-driven dev »

Vibe coding AI-driven dev
Logique explorer vite produire de façon fiable
Pour spike, POC jetable, script ponctuel fonctionnalité livrée dans un code existant
Exemple « fais-moi une API de démo » paginer GET /bookings, avec ses tests
Réflexe on tente, on observe, on jette on cadre, on vérifie, on capitalise

Viber pour explorer, piloter pour livrer. Cette formation est du côté droit : livrer en restant à gauche, c’est accepter du code qu’on n’a ni relu ni vérifié.

La boucle, tour par tour

Ouverture · slide « La boucle, tour par tour »

Rappel de la Foundation, sur l’exemple du fil rouge : « Ajoute la pagination sur l’endpoint /bookings ».

  1. Le harness envoie la demande et la liste des tools.
  2. Le modèle répond « j’appelle bash avec npm test -- bookings ».
  3. Le harness vérifie que c’est autorisé, exécute, récupère la sortie : un test échoue, nextCursor is undefined.
  4. Il renvoie tout au modèle (le modèle est sans état), plus la sortie.
  5. Le modèle demande à lire le fichier du test, et ainsi de suite jusqu’à une réponse sans appel de tool.
  • Le « appel de tool ? » est un champ de la réponse de l’API (stop_reason: "tool_use" chez Anthropic, finish_reason: "tool_calls" chez OpenAI).
  • La même boucle porte plusieurs noms : ReAct (Pensée → Action → Observation), Plan-and-Execute, ou « gather context → take action → verify work → repeat ». Tous décrivent le même mécanisme : planifier, agir, observer le résultat, réajuster.
  • À chaque tour, le contexte grossit : c’est tout le sujet de ce module.

Qui parle à qui : la pile complète

Module 1 · slide « Qui parle à qui : la pile complète »

Une requête descend la pile, de la méthode jusqu’au fournisseur :

Couche Rôle
Méthode (SDD) spec.md → plan.md → tasks.md, relus par l’humain
Orchestrateur découpe, distribue, attend, agrège, reprend sur erreur
Agent = harness boucle, tools, contexte ; appelle le modèle
Gateway + guardrails auth, routage, quotas, cache, journalisation, filtrage entrée / sortie
Fournisseurs LLM cloud, hyperscaler, souverain, SLM local
  • Les tools (fichiers, terminal, git, navigateur, serveurs MCP) sont exécutés par le harness, jamais par le modèle : le modèle n’écrit qu’une demande d’appel. C’est fondamental pour la sécurité.
  • La gateway est le seul point par lequel tout passe : l’endroit naturel de la gouvernance (module 6).
  • Seul sur son poste, un dev n’a souvent ni méthode, ni orchestrateur, ni gateway : la pile se construit à mesure qu’on industrialise.

Harness vs orchestrateur : la frontière

Module 1 · slide « Harness vs orchestrateur : la frontière »

Harness Orchestrateur
Fait d’un modèle un agent travailler plusieurs agents
Responsabilités gère une boucle d’agent ; exécute les tools, applique les permissions ; construit et compacte le contexte décompose et route les tâches ; parallélise, attend, agrège ; persiste l’état, reprend après panne
Se pilote depuis un terminal, un IDE ou une API en code, en graphe ou en YAML
Exemples Claude Code, Codex CLI, Copilot CLI, OpenCode LangGraph, CrewAI, OpenAI Agents SDK, Temporal

La frontière bouge : les harness lancent des sous-agents, les orchestrateurs embarquent leur boucle. Retenez le rôle, pas le produit. Ce qu’un orchestrateur dédié apporte en plus : la persistance d’état et la reprise après panne.

KV cache : ne pas tout recalculer à chaque token

Module 1 · slide « KV cache : ne pas tout recalculer à chaque token »

Une réponse se fait en deux temps : le prefill (lire tout le contexte, en parallèle) puis le decode (générer token par token). Pour chaque nouveau token, le modèle a besoin des clés et valeurs (K, V) de tous les tokens précédents ; elles ne changent plus une fois calculées, on les garde en mémoire GPU : c’est le KV cache.

Point Ce qu’il faut savoir
Sans cache chaque token recalculerait K et V de tous les précédents : un coût quadratique
Le prix Llama 3 8B : 128 Ko par token, 16 Go pour 128 k tokens, pour une seule conversation
Les parades têtes K/V partagées (GQA), cache quantifié, mémoire paginée (PagedAttention)

Les deux chiffres des benchmarks en découlent : le TTFT (time to first token, le prefill) et le débit en tokens/s (le decode).

Du KV cache au prompt caching

Module 1 · slide « Du KV cache au prompt caching »

Le prompt caching : le fournisseur garde le KV cache d’un préfixe déjà vu. Même début de requête, le prefill est sauté : plus rapide, et ~90 % de remise sur l’entrée lue en cache.

Anatomie d’une requête d’agent, du plus stable au plus volatil :

  1. System prompt
  2. Tool definitions
  3. Instructions projet
  4. Conversation + résultats des tools
  5. Nouveau message
  • Modifier le début casse le cache pour tout ce qui suit : changer le system prompt, ajouter ou retirer un serveur MCP (donc des tool definitions), changer de modèle, mettre l’heure exacte dans les instructions.
  • Cache expiré : l’agent n’a rien oublié, la conversation est renvoyée en entier. Mais le préfixe est repayé plein tarif, et la réponse arrive plus tard.
  • Durée de vie : de quelques minutes à quelques heures sans activité, selon le fournisseur et l’option choisie. Remises et durées changent souvent : retenez l’ordre de grandeur.

Avant une longue pause (qui casse le cache) : tâche finie → repartir sur une session propre ; tâche en cours → compacter, pour revenir sur un contexte court. La commande de chaque harness est dans « Où ça se règle dans mon outil ».

Ce que coûte cette trace

Module 1 · slide « Ce que coûte cette trace »

La trace de la Foundation : sept tours d’un agent qui ajoute la pagination par curseur sur GET /bookings. Contextes envoyés de 12 k à 21 k tokens, soit 118 k tokens d’entrée cumulés pour une tâche simple.

Point Ce qu’il faut savoir
Le constat l’entrée fait le volume : chaque tour renvoie tout le préfixe déjà vu, et n’ajoute que quelques milliers de tokens
Avec le prompt caching ce préfixe est lu en cache, à ~10 % du prix
La sortie ~5× plus chère au token, mais petite en volume

Où part la facture d’une session :

Élément Sur toute la session
System prompt, tool definitions, AGENTS.md gros mais stable : lu en cache
Historique des tours précédents en cache, si rien ne change avant
Fichier lu en entier, log de build de 3 000 lignes payé plein tarif une fois, puis renvoyé à chaque tour : il pèse sur toute la fin de la session
Nouvelle demande plein tarif, mais petite
Réponse et tokens de raisonnement prix de sortie ; le raisonnement est souvent invisible

Réduire ce qui entre rapporte plus que raccourcir la sortie : sorties de tools filtrées, fichiers lus en partie, session propre, modèle adapté.

Pour mesurer sa propre facture : chaque harness affiche la consommation de la session, et des outils recalculent à partir des logs locaux (ex. ccusage). On mesure son usage, on ne compare pas les outils.

Tokens de raisonnement : choisir l’effort

Module 1 · slide « Tokens de raisonnement : choisir l’effort »

Le modèle « réfléchit » en tokens avant de répondre. Ces reasoning tokens sont facturés comme de la sortie (×5 face à l’entrée), et souvent invisibles : masqués, résumés ou affichés selon le fournisseur.

Effort · classe de modèle Pour
Bas · modèle léger renommer, documenter, appliquer un pattern
Moyen · généraliste paginer un endpoint et ses tests, relire un diff
Haut · raisonnement bug difficile, migration, architecture

L’effort se choisit par tâche : plus lent, plus cher, et pas toujours meilleur. Sur une tâche simple, trop de raisonnement mène à la sur-ingénierie et aux détours.

Bon réflexe : commencer au niveau moyen, monter quand l’agent échoue sur un problème réellement difficile. Les harness appellent ce réglage effort, thinking ou niveau de raisonnement : voir « Où ça se règle dans mon outil ».

Les SLM : petits, locaux, spécialisés

Module 1 · slide « Les SLM : petits, locaux, spécialisés »

Point Ce qu’il faut savoir
Définition pratique de ~1 à ~15 milliards de paramètres : assez petit pour tourner sur un poste ou un seul GPU (la frontière n’est pas normalisée)
Exemples Gemma 4, Qwen3.5, Phi-4-mini, Granite 4, Ministral
Bons cas d’usage classer, extraire, router, compléter du code, données qui ne sortent pas
Limites raisonnement long, agents autonomes sur de gros dépôts
Pour les faire tourner Ollama, LM Studio, llama.cpp sur le poste ; vLLM sur un serveur
  • Pattern hybride : le SLM trie et route, le LLM raisonne.
  • Argument entreprise : un SLM sur un serveur interne ne fait sortir aucune donnée, et son coût est fixe (le matériel), pas à l’usage.

Tip du module : garde le début du contexte stable, c’est lui que le cache rentabilise. Instructions, tools et modèle fixés en début de session ; ce qui change va à la fin.

À retenir

  1. Le modèle prédit, le harness agit : il exécute les tools et construit le contexte.
  2. Le KV cache évite de recalculer ; le prompt caching rentabilise un préfixe stable.
  3. En session, l’entrée fait le volume ; la sortie et le raisonnement sont chers au token.
  4. Modèle et effort se choisissent par tâche, du SLM au modèle de raisonnement.

Mots-clés : prefill, decode, KV cache, prompt caching, reasoning tokens, SLM, harness, orchestrateur, gateway — voir le glossaire.

Le harness

Quelles briques entourent le modèle, et laquelle utiliser pour quoi : cette fiche reprend le module 2, des capacités d’un harness jusqu’à ce qu’il injecte dans la context window.

Les capacités attendues d’un harness

Module 2 · slide « Les capacités attendues d’un harness »

Agent = modèle + tools + boucle + objectif, comme en Foundation ; c’est le harness qui fournit les tools et fait tourner la boucle. Le modèle raisonne ; le harness lui donne les moyens d’agir. Un même modèle dans deux harness peut donner des résultats très différents, en coût comme en réussite.

La grille pour évaluer n’importe quel harness, y compris ceux qui n’existent pas encore :

Capacité Ce qu’on vérifie
Sous-agents contexte isolé, et le droit d’écrire (un sous-agent en lecture seule sait relire, pas corriger)
MCP standard n’importe quel serveur, déclaré dans un fichier versionné
Instructions, skills, hooks personnaliser sans toucher au cœur
Modes de pilotage monter l’autonomie, borner les droits
Scriptable un mode non interactif, pour la CI

Deux philosophies, qui ne s’opposent pas frontalement :

  • Plateforme (ex. GitHub Copilot, Claude Code) : un harness intégré qui décide de la structure ; Copilot l’étend jusqu’à la forge (issues, PR, CI).
  • Composition (ex. Pi, OpenCode) : un cœur minimal, des extensions, multi-fournisseur ; on compose son harness.

Dans les deux cas, le harness est un actif d’équipe versionné. Sinon, c’est de l’agentic debt : extensions qu’on ne comprend plus, contournements de permissions oubliés, instructions contradictoires empilées. Même remède que la dette technique : versionner, relire, supprimer.

Un seul jeu d’artefacts versionné (AGENTS.md, SKILL.md, configuration MCP) sert de plus en plus de harness : voir « Où ça se règle dans mon outil ».

Une allowlist n’est pas une sandbox

Module 2 · slide « Une allowlist n’est pas une sandbox »

Allowlist Sandbox
Agit sur des motifs de commande les effets : fichiers, réseau, droits
Contournement npm test && curl …, un script qui en appelle un autre aucun par le prompt : l’agent ne sort pas du périmètre
Forme une liste dans la config du harness conteneur, VM, compte dédié, réseau coupé

Le seul périmètre réel est l’isolation. Une allowlist filtre le texte d’une commande, pas ce qu’elle fait : on autorise npm test, et un script de test modifié par l’agent peut faire n’importe quoi, avec vos droits.

  • « La policy vit dans le runtime, pas dans le prompt » : une consigne « ne lance jamais de commande destructrice » dans AGENTS.md n’est qu’une suggestion.
  • MCP n’apporte rien sur ce terrain : le protocole standardise le branchement des tools, pas leurs permissions.
  • Autonomie et droits sont deux réglages distincts. Les niveaux d’autonomie (observer, demander, agir dans le périmètre, aller au bout seul) existent dans tous les harness, sous des noms différents. On monte d’un niveau quand on fait confiance au périmètre, et jamais « sans demander » sans isolation. Ce qui rend la montée acceptable, c’est le filet : tests, commits fréquents, diff relu, hook de vérification.

Les primitives du harness : qui décide ?

Module 2 · slide « Les primitives du harness : qui décide ? »

Primitive Ce que c’est Qui décide qu’elle s’applique Exemple sur l’API du fil rouge
Instructions projet AGENTS.md : règles stables, conventions, commandes personne : toujours chargées « les endpoints suivent le contrat OpenAPI »
Skill savoir-faire réutilisable, chargé quand la tâche s’y prête le modèle, sur sa description la procédure pour ajouter une migration
Hook script lancé à un moment précis du cycle de vie le harness, à chaque événement lancer les tests après chaque édition
Sous-agent travail à part, ne renvoie que son résultat l’agent ou toi explorer le module bookings sans polluer la session
MCP accès à un système externe le modèle, à la demande lire le ticket dans le tracker

Le critère qui range tout : qui décide qu’une primitive s’applique.

  • Règle de base : règles stables → instructions projet ; savoir-faire → skill ; ce qui doit arriver à coup sûr → hook ; travail à isoler → sous-agent ; système extérieur → MCP.
  • L’erreur classique : tout mettre dans AGENTS.md, qui pèse dans chaque appel. AGENTS.md = ce qui est toujours pertinent ; skill = ce qui l’est parfois (sa description est un prompt) ; hook = ce qui doit arriver sans que personne y pense.
  • La demande initiale n’est pas une primitive du harness : c’est le premier message, cadré pour la tâche du jour (fichiers clés, tests et invariants). Elle évite de gonfler AGENTS.md avec du contexte éphémère.
  • Le mot « agent » désigne au moins trois choses : l’agent de code, le sous-agent à contexte isolé, l’agent personnalisé d’un outil. Vérifiez duquel on parle.
  • Formats ouverts d’abord : AGENTS.md et SKILL.md sont lus par la plupart des harness ; l’emplacement des hooks et des sous-agents varie.

Hooks : automatiser le cycle de vie

Module 2 · slide « Hooks : automatiser le cycle de vie »

Des scripts déterministes, lancés par le harness, quoi que dise le modèle. Le socle commun à tous les harness :

Événement Usage Exemples
Avant un tool bloquer git push --force, rm -rf, ou réécrire une commande verbeuse
Après un tool formater le fichier écrit, ou journaliser l’appel
Fin de tour vérifier lancer les tests, relire le diff produit
Fin de session archiver la trace, ou proposer une mise à jour des notes

« Lance toujours les tests » dans les instructions est une suggestion. Le hook est une garantie.

  • Le hook d’avant un tool peut renvoyer une décision (autoriser, demander, refuser) et donc bloquer l’appel de façon déterministe ; il peut aussi réécrire les arguments.
  • Piège de nommage : la « fin de tour » se déclenche quand l’agent a fini sa réponse, pas au git commit. Pour contrôler le commit, visez le hook d’avant un tool sur la commande git, ou un hook git classique.
  • Piège CI : en mode non interactif, certains harness ne chargent pas par défaut les hooks du dépôt, par sécurité. Un hook qui marche en local peut être absent en CI.
  • Les noms d’événements varient d’un harness à l’autre : voir « Où ça se règle dans mon outil ».

Tool calling : ce qui transite réellement

Module 2 · slide « Tool calling : ce qui transite réellement »

Trois messages, au format simplifié de l’API Messages d’Anthropic ; OpenAI et Google utilisent des structures équivalentes, d’où la possibilité pour une gateway de traduire d’un format à l’autre.

① Le harness déclare le tool :

{
  "name": "run_tests",
  "description": "Lance les tests",
  "input_schema": {
    "type": "object",
    "properties": { "path": { "type": "string" } }
  }
}

② Le modèle demande :

{ "type": "tool_use", "id": "call_01", "name": "run_tests", "input": { "path": "tests/bookings" } }

③ Le harness répond :

{ "type": "tool_result", "tool_use_id": "call_01", "content": "FAIL bookings:42 nextCursor is undefined" }

Le modèle choisit sur la description : chaque tool definition part en tokens à chaque appel.

  • Une mauvaise description = un tool mal utilisé ou ignoré. Quand vous écrivez un serveur MCP ou une skill, soignez la description : c’est un prompt.
  • 40 tools MCP branchés = des milliers de tokens de préfixe, à chaque appel. Certains harness chargent désormais les tool definitions à la demande : à vérifier sur son outil.

Ce que le harness injecte

Module 2 · slide « Ce que le harness injecte »

Une session agentique remplit la context window avec bien plus que vos messages :

Bloc Ce qu’il apporte Réflexe
System prompt les règles du harness ouvrent la session —
Tool schemas chaque tool et chaque serveur MCP branché prend de la place, même s’il ne sert pas aujourd’hui couper les MCP inutiles pour la tâche
Fichiers lus du code brut, pertinent ou non lire en partie
Sorties de commandes un build, un npm install ou une stack trace peuvent dominer la context window demander une sortie filtrée (erreurs seules, 20 dernières lignes), ou filtrer par un hook
Logs d’erreur les erreurs répétées deviennent du bruit les faire synthétiser
Résultats de tests utiles, mais consomment aussi du budget —

La question n’est pas « l’agent est-il intelligent ? », mais « ce qu’il a injecté aide-t-il la tâche ? »

Avant de brancher un serveur MCP, trois questions : qui l’exécute ? (un processus local ne sort pas de la machine, un serveur distant reçoit ce que le modèle choisit de lui envoyer) ; qui l’authentifie ? (quel jeton, quels droits : jamais plus large que la tâche) ; qui le maintient ? (éditeur officiel ou fork communautaire). Le trio létal (données privées + contenu non fiable + capacité d’envoyer vers l’extérieur) se réunit souvent par MCP.

Une primitive par besoin

Module 2 · slide « Quiz : quelle primitive ? »

La grille appliquée à des besoins réels :

Besoin Primitive Pourquoi
« Toujours passer par le client HTTP interne » instructions projet vrai à chaque tâche ; on peut le doubler d’une règle de lint, déterministe
Interdire git push --force, quoi qu’il arrive hook doit arriver à coup sûr
Migrer le schéma, une fois par mois skill savoir-faire chargé seulement quand la tâche s’y prête
Explorer 40 fichiers sans polluer la session sous-agent contexte isolé, ne renvoie que son résultat

Tip du module : ce qui doit toujours arriver est un hook, pas une consigne. Une consigne, le modèle peut l’oublier ; un hook, c’est le harness qui l’exécute.

L’exercice 1 met cette règle en pratique : voir « Les exercices ».

À retenir

  1. Un harness s’évalue sur ses capacités, pas sur sa marque ; non versionné, il devient de l’agentic debt.
  2. Une allowlist filtre des commandes, une sandbox borne les effets : seule l’isolation est un périmètre.
  3. Chaque primitive se range par qui décide : personne, le modèle, le harness, l’agent, ou toi.
  4. Chaque tool branché pèse dans chaque appel, et sa description est un prompt.

Ingénierie du contexte

La context window est un budget : cette fiche reprend le module 3, pour donner à l’agent le bon contexte, au bon moment, au bon coût.

Ce qui entre dans la context window

Module 3 · slide « Ce qui entre dans la context window »

Élément Entre quand ? Ensuite
AGENTS.md, tool definitions au démarrage dans chaque appel, en cache
Historique à chaque échange grossit, compacté près de la limite
Fichiers lus, sorties de tools à la demande renvoyés jusqu’à la fin de la session
Skills quand le modèle les juge utiles nom et description d’abord, contenu ensuite (progressive disclosure)

Pour le savoir : regarder la jauge, demander à l’agent ce qu’il a lu, élaguer ce qui ne sert plus.

  • Regarder : l’occupation du contexte, les tool calls, les fichiers lus ; la plupart des harness les affichent (voir « Où ça se règle dans mon outil »).
  • Demander : « Quels fichiers as-tu lus ? Sur quelle hypothèse pars-tu ? »
  • Élaguer : MCP inutiles, vieux objectifs, gros logs, par un rewind ou une session propre.
  • Un fichier lu reste dans la context window jusqu’à la fin de la session (ou la compaction) : lire 3 000 lignes pour y trouver une fonction, c’est les repayer à chaque tour.

Ce qui s’accumule au fil d’une session, ou pas :

Ressource Au fil des échanges
Temps de calcul le préfixe ne se recalcule pas (le KV cache le garde), mais chaque token généré relit tout le cache : plus le contexte est long, plus la réponse ralentit
Mémoire GPU s’accumule jusqu’à la limite de la context window ; au-delà, le harness compacte ou on repart propre
Facturation réduite : le préfixe déjà vu est lu en cache, tant que le début du contexte ne change pas
Attention du modèle se dégrade (lost in the middle, context rot) : compacter restaure aussi la fiabilité, pas seulement le coût

La taille des context windows (de ~128 k à ~1 M tokens selon les modèles) bouge à chaque génération ; la qualité baisse avant même la limite.

Avec ou sans demande initiale

Module 3 · démo « Avec ou sans demande initiale »

La même tâche, deux sessions propres : on compte les fichiers lus et le contexte consommé avant le premier plan, et on juge la justesse du plan.

Une demande initiale cadrée donne à l’agent l’objectif, les fichiers clés, les commandes, les invariants et les pièges. Les deux demandes à coller et le relevé à remplir sont dans le handout « Les démos », pour rejouer la démo.

  • Une demande initiale est orientée tâche, pas dépôt ; courte et relue. Les noms (chemin, commande, invariant) sont des ancres. Pour une tâche longue, on l’écrit dans un fichier rechargé à chaque session.
  • En la relisant, on découvre souvent les zones floues du projet, avant de lancer l’agent.

Le gain annoncé n’est pas le gain mesuré : on compte. Sur un petit dépôt, la recherche agentique suffit souvent.

Réduire les tokens : un levier par buffer

Module 3 · slide « Réduire les tokens : un levier par buffer »

Buffer Levier Comment
Sorties de tools filtrer erreurs seules, dernières lignes
Données lourdes traiter hors contexte un script, un index
Entre sessions mémoire ciblée ne plus tout réexpliquer
Réponse demander du concis pas de préambule
Code généré en écrire moins moins à relire ensuite

Comprimer la prose du modèle rapporte peu : l’entrée domine. Faire écrire moins de code rapporte deux fois : maintenant et à la relecture.

  • Les outils changent, les buffers restent : chaque levier existe sous forme de plugin, de hook ou de skill dans l’écosystème.
  • Lire les chiffres avec esprit critique : les gains annoncés sont mesurés en conditions de pointe, pas en moyenne de session, et ne s’additionnent que si votre usage déclenche vraiment chaque levier. Entre un outil très populaire au gain fragile et un outil discret au gain vérifié, choisissez le second.
  • Rendre la consommation visible la réduit déjà : voir la context window se remplir pousse à compacter, repartir propre, mieux cadrer.

Deux lignes à coller dans AGENTS.md, qui captent l’essentiel du gain d’un plugin de concision :

Réponds de façon dense et factuelle. Pas de préambule, ne reformule
pas ma question, pas de hedging. Une phrase = une information.

Le piège des sous-agents

Module 3 · slide « Le piège des sous-agents »

Un cas vécu : une demande de recherche un peu large → 6 sous-agents lancés en parallèle → chacun charge toutes les pages qu’il lit → 1 M de tokens en 30 min, quota épuisé.

  • La jauge de la session principale allait très bien : chaque sous-agent brûlait dans sa propre context window.
  • La vue de la context window ne montre pas ce que consomment les sous-agents : regardez la consommation totale de la session (la plupart des harness la ventilent par sous-agent).
  • En facturation à l’usage, sans quota, la même situation donne une facture sans plafond.
  • On borne périmètre et nombre d’agents avant de lancer, avec un périmètre écrit.

Un sous-agent protège ta context window, pas ton budget : déléguer est une décision de coût.

RAG : le retour des embeddings

Trois familles, du plus explicite au plus automatique, et aucun standard :

  • Le bon mécanisme est la progressive disclosure : chercher dans un index compact, puis ne charger que le détail des entrées retenues, pour ~10× moins de tokens. Même pattern que le RAG et les skills : filtrer avant de charger.

Une session contient ce qui a été tenté et ce qui a échoué, ce qui manquait (doc, tool, convention), ce qui a fini par marcher : c’est de l’inférence déjà payée. On en extrait du contexte durable, relu, puis on jette la session.

Ce que l’IA change dans notre façon de travailler

Module 4 · slide « Ce que l’IA change dans notre façon de travailler »

L’agent a compressé le temps de production, pas celui de vérification.

Hier Avec un agent
Rythme une feature = des jours une feature = des heures
Ce qui garantit revues et rituels, a posteriori contrôles systématiques, à chaque étape

Les revues ne disparaissent pas : elles ne suffisent plus seules. On leur adjoint des contrôles automatiques, au rythme de l’agent.

  • Nos garanties sont des rendez-vous humains, après coup, à intervalle fixe. Quand le volume produit entre deux rendez-vous est multiplié, le rendez-vous devient un goulot, puis une formalité.
  • Le systématique prend ce qui se vérifie mécaniquement (les tests passent-ils ? la spec est-elle à jour ?) ; le temps humain garde l’intention, l’architecture, les arbitrages.

Le SDD est une réponse possible : une chaîne d’artefacts relus par un humain, chaque sortie est un fichier versionné.

Étape Produit Contenu
Spécifier spec.md le quoi et le pourquoi
Planifier plan.md le comment technique
Découper tasks.md de petites tâches vérifiables
Implémenter code + tests un agent, ou des workers par tâche

Le SDD donne aux agents un objectif écrit et un critère d’arrêt. Outillage, par exemple : Spec Kit, Kiro, OpenSpec, BMAD ; ils fonctionnent au-dessus de n’importe quel harness.

Trois postures face à la spec

Module 4 · slide « Trois postures face à la spec »

SDD : la spec versionnée est la source de vérité que l’agent implémente et que les tests vérifient.

Posture La spec Le risque
Spec-first écrite d’abord, comme prompt structuré ; non maintenue elle diverge du code
Spec-anchored spec et code évoluent ensemble les écarts sont détectés
Spec-as-source seule la spec est éditée ; le code devient un artefact généré aucun framework ne le fait (encore) : il faudrait rejouer tous les changements de spec

Cible réaliste : spec-anchored. L’agent sait formaliser une spec, pas décider ce qui doit être vrai.

  • Un curseur de maturité, pas un interrupteur : on démarre en spec-first, on consolide en spec-anchored.
  • L’agent formalise volontiers : critères d’acceptation, cas limites (curseur invalide, limit négatif, tri instable), dépendances repérées dans le code. Il ne peut pas décider si un curseur invalide doit renvoyer 400 ou la première page : c’est une décision humaine.
  • Une spec générée et non relue est une hypothèse, pas une source de vérité. Bon usage : demander à l’agent de lister les questions ouvertes, plutôt que de les trancher.
  • La connaissance se perd à chaque passage de main (intention → ticket → dev → agent → code), et l’agent comble les trous avec du plausible : d’où une intention écrite une fois, versionnée, relue.
Écris une spec de moins de 30 lignes pour ce besoin : contexte,
exigences numérotées, critères d'acceptation, questions ouvertes.
Ne tranche pas les questions ouvertes. Ne code rien.

Spec-centric ou workflow-centric

Spec-centric Workflow-centric
Exemples Spec Kit, OpenSpec, BMAD Superpowers

Pas un concurrent à départager : les deux se combinent. La spec quand elle doit survivre à la session ; le workflow pour une exécution serrée sur une tâche bornée.

La spec n’est qu’une partie de la doc : elle décrit le quoi. Ce qu’on conserve dans le temps, c’est la documentation, fonctionnelle (critères d’acceptation) et technique (architecture, invariants, ADR, runbooks), tenue à jour. Le code est un artefact que la doc permet de reprendre.

Garde-fous : du code au commit

Module 4 · slide « Garde-fous : du code au commit »

L’agent génère vite : sans garde-fou, l’écart avec l’intention passe inaperçu.

Garde-fou Ce que c’est Vérifie
1. Tests le contrat exécutable le comportement
2. Revue agentique par un agent distinct de celui qui a écrit le code le diff, avant d’envoyer
3. Commit le point de synchronisation entre code, spec et IA la doc suit, la part d’IA est tracée

Règle minimale : aucun code généré ne part en production sans vérification déterministe (tests, analyse statique) et revue par un agent distinct.

  • Les trois niveaux sont complémentaires. Ordre dans un pipeline : le déterministe d’abord (lint, types, tests, mutation), l’agentique ensuite, l’humain en dernier. Un agent de revue doit avoir le droit de ne rien dire sur un diff propre.
  • Traçabilité IA au commit : le trailer Co-Authored-By: est une convention git standard (qui a écrit), que certains harness posent nativement ; un footer comme AI-Generated: ~80% est une convention d’équipe, approximative (combien).
  • La spec à jour ? Un contrôle au commit compare le diff et la spec, et bloque si une mise à jour est attendue : un hook (avant le tool git commit), un hook git classique ou un job de CI.

Tests générés : deux natures, une mesure

Module 4 · slide « Tests générés : deux natures, une mesure »

Tests de construction Tests fonctionnels
Servent à l’agent à l’équipe
Testent l’implémentation, unité par unité les effets observables
Durée de vie jetables durables : la spec exécutable
Exemple « le repository reçoit le bon curseur » « GET /bookings renvoie un nextCursor tant qu’il reste des résultats »

En fin de feature, là où les deux se recouvrent, le test fonctionnel gagne : on supprime le doublon de construction.

  • Le critère n’est pas « unitaire vs intégration », mais à qui le test rend service. Un test fonctionnel survit à une réécriture de l’implémentation ; on le relit ligne à ligne.
  • Le symptôme d’une suite générée trop couplée : toucher une ligne casse dix tests (mocks partout, une classe = un test). Le coût de production d’un test a chuté, son coût de maintenance n’a pas bougé.
  • Score de mutation : on modifie le code exprès (< devient <=), la suite doit échouer. Bien plus dur à tricher que la couverture, qu’un agent peut faire monter sans rien vérifier. Outils : Stryker (JS/TS, .NET), PIT (Java), mutmut (Python), cargo-mutants (Rust). Cadence réaliste : nocturne, sur les modules critiques.

Le drift spec ↔ code : qui le détecte ?

Module 4 · slide « Le drift spec ↔ code : qui le détecte ? »

Drift : l’écart qui s’installe entre la spec et le code. (On dit « context rot » pour la dégradation d’une session, pour ne pas confondre.)

Détecteur Ce qu’il voit Ce qu’il rate
Tests fonctionnels un comportement qui contredit une exigence encodée une exigence nouvelle, sans test
Revue de spec dans la PR un diff qui ne raconte pas la même chose que la spec ce que le relecteur n’a pas lu
Contrôle au commit du code changé sans spec touchée une spec touchée… mais fausse
Personne — tout : le drift est silencieux

Quand une exigence change, c’est la revue de spec qui le voit d’abord. Aucun détecteur ne suffit seul.

Exemple : l’exigence « curseur invalide → 400 » devient « curseur invalide → première page ». Code changé sans la spec : le test fonctionnel casse (bonne nouvelle). Spec changée sans le test : rien ne casse, seul un relecteur de la spec le voit.

Tip du module : si la spec n’est pas versionnée avec le code, elle ment déjà. Spec, tests et commit dans le même dépôt, c’est ce qui rend le drift visible.

L’exercice 2 fait changer une exigence en cours de route : voir « Les exercices ».

À retenir

  1. L’agent compresse la production, pas la vérification : on ajoute des contrôles au rythme de l’agent.
  2. Cible réaliste : spec-anchored ; l’agent formalise, l’humain décide ce qui doit être vrai.
  3. Garde-fous dans l’ordre : déterministe, agentique, humain ; le commit trace la part d’IA.
  4. Les tests fonctionnels durent, les tests de construction se jettent ; le score de mutation mesure leur vraie valeur.

Quand découper le travail en plusieurs agents, et à quel prix : cette fiche reprend le module 5, des patterns d’orchestration au coût caché du parallélisme.

Cinq patterns d’orchestration

Module 5 · slide « Cinq patterns d’orchestration »

Les cinq patterns de « Building effective agents » (Anthropic, 2024). Les cinq sont des workflows, du plus figé (chaîne : chemin connu à l’avance) au plus dynamique (orchestrateur-workers, évaluateur : un LLM décide du découpage ou de l’arrêt). L’agent autonome, qui choisit lui-même ses étapes, vient ensuite.

Pattern Principe Exemple dev
Chaîne étapes fixes, chaque sortie nourrit la suivante le flux SDD : spec → plan → tâches → code, chaque étape relue
Routeur un classifieur oriente vers le bon agent ou le bon modèle les demandes simples vont à un modèle léger, les complexes à un modèle de raisonnement
Parallélisation tâches indépendantes, ou vote entre plusieurs, puis agrégation trois revues du même diff : sécurité, performance, lisibilité
Orchestrateur-workers le découpage est décidé dynamiquement par un LLM les sous-agents d’un harness : l’agent principal décide combien en lancer et ce que fait chacun
Évaluateur un générateur, un évaluateur ; on itère jusqu’au critère un agent écrit l’endpoint, un autre le relit avec une grille
  • Parallélisation et orchestrateur-workers se ressemblent ; dans le second, c’est le modèle qui décide du découpage, pas le développeur.
  • Le conseil de l’article : commencer simple, n’ajouter un agent que si l’avantage est démontré.

La fiabilité composée : 10 étapes à 95 % ≈ 60 %

Module 5 · slide « La fiabilité composée : 10 étapes à 95 % ≈ 60 % »

Fiabilité d’une chaîne d’agents fiables à 95 % chacun :

Étapes 1 2 3 5 10
Fiabilité 95 % 90 % 86 % 77 % 60 %

Les fiabilités se multiplient : 0,95 × 0,95 × … dix fois ≈ 0,60. La parade : une chaîne courte, et une vérification entre les étapes.

  • L’hypothèse est simplificatrice (étapes indépendantes, une erreur = un échec), mais l’ordre de grandeur suffit à calmer l’envie d’empiler les agents.
  • Une vérification entre deux étapes (tests, évaluateur, relecture) remet la fiabilité de l’étape près de 100 % : c’est pour ça que les tests comptent tant.
  • L’échelle de construction : appel direct → tools → workflow déterministe dès qu’il faut des étapes et des validations explicites → agent supplémentaire seulement si l’avantage est démontré.

Agents en parallèle sur worktrees

Module 5 · slide « Agents en parallèle sur worktrees »

Un dépôt, deux répertoires de travail, deux agents en même temps. Un git worktree est un deuxième répertoire de travail rattaché au même dépôt : même historique, autre branche.

Worktree A Worktree B
Branche feat/bookings-pagination feat/bookings-export
Agent pagination par curseur export CSV
Fin revue · merge · nettoyage revue · merge · nettoyage

Paralléliser demande d’isoler : chaque agent a ses fichiers, sa branche et son contexte.

Ce qui est portable d’un harness à l’autre, c’est git : plusieurs éditeurs et harness créent désormais un worktree par session parallèle (voir « Où ça se règle dans mon outil »).

Développement parallèle : le bilan

Module 5 · slide « Développement parallèle : le bilan »

Ce qu’on gagne Ce que ça coûte
Temps : deux features avancent ensemble Tokens × n : chaque agent a son propre contexte
Isolation : les agents ne se perturbent pas Conflits de merge : si les features touchent les mêmes fichiers
Revue : des PR plus petites, plus lisibles Services partagés : ports, base de données, dépendances

Features indépendantes seulement. Et ce qui sature d’abord, c’est vous : au-delà de 2 sessions, on subit.

  • Quand ça vaut le coup : features vraiment indépendantes (modules distincts), plus de 15 à 20 min d’agent chacune, équipe à l’aise avec le merge.
  • Déconseillé : services partagés (bases, ports), dépendances très lourdes à réinstaller par worktree.
  • La limite du parallélisme n’est pas la machine : c’est la capacité de revue humaine. Sans méthode, l’IA peut même ralentir : dans l’étude METR (juillet 2025, 16 développeurs, 246 tâches), les développeurs avec IA ont pris 19 % plus longtemps.

Le coût caché : l’érosion de la connaissance

Module 5 · slide « Le coût caché : l’érosion de la connaissance »

Effet Ce qui se passe
Écrire moins le code vous appartient moins quand vous ne l’écrivez pas
Relire n’est pas apprendre on valide une forme, pas un raisonnement
Lent et invisible on le découvre en incident, deux ans plus tard

Ce n’est pas un argument contre l’autonomie, c’est sa condition : ce qu’on automatise, il faut savoir le reprendre.

  • L’IA amplifie ce que vous êtes déjà : bonne base de code → meilleure ; mauvaise → bien pire.
  • La documentation est ce qui reste quand la mémoire de l’équipe s’efface (module 4). Supprimer la revue humaine, c’est perdre le principal moment où la connaissance circule.
  • Deux questions à se poser : sur le code que votre agent a produit la semaine dernière, lequel sauriez-vous expliquer à un collègue ? Qui saurait reprendre ce module sans l’agent ?

Superviser au lieu d’approuver

Module 5 · slide « Quiz : quel pattern ? » (tip du module)

Deux moyens au service du même saut d’autonomie, adoptables séparément :

  • Le poste comme console : sessions persistantes, une par panneau de terminal ou d’éditeur ; on voit ce que l’agent fait, on ne le devine pas ; le diff est relu ligne à ligne avant de valider.
  • Le parallélisme, quand c’est indépendant : worktrees, une branche isolée par agent, des PR plus petites, des contextes ciblés.

Ce qui rend l’autonomie tenable, ce n’est pas l’outillage : ce sont les tests, les commits fréquents et la relecture du diff. Sans ce filet, monter d’un cran ne fait qu’accélérer la production de code non vérifié.

Tip du module : superviser au lieu d’approuver, ajoute un agent seulement si tu sais qui relira son travail.

À retenir

  1. Cinq patterns, du plus prévisible au plus autonome : commencer simple.
  2. Les fiabilités se multiplient : chaîne courte, vérification entre les étapes.
  3. Paralléliser demande d’isoler ; au-delà de deux sessions, c’est la revue qui sature.
  4. L’autonomie a une condition : savoir reprendre ce qu’on automatise.

Où placer les contrôles

Module 6 · slide « Où placer les contrôles »

Garde Ce qu’elle contrôle
Garde d’entrée injection, jailbreak ; données perso, secrets → masquer ; sujets interdits ; taille, débit, budget
Garde de sortie toxicité, hors périmètre ; fuite de données ; ancrage (grounding) ; format / schéma valide
Garde d’action liste blanche de tools ; sandbox, conteneur, réseau ; droits minimaux (tokens) ; validation humaine

Les gardes d’entrée et de sortie réduisent le risque. La garde d’action le borne : un agent sans réseau ne peut pas exfiltrer.

  • Défense en profondeur : aucun étage n’est suffisant seul.
  • Les gardes d’entrée et de sortie sont souvent elles-mêmes des modèles (classifieurs, petits modèles), donc faillibles, avec de la latence et du coût. On les place sur les données externes non fiables (prompt injection) et sur les sorties qui partent vers des clients.
  • La garde d’action est déterministe : un refus sur git push ne se contourne pas par un prompt astucieux. Pour un agent de code, c’est le premier investissement : permissions du harness, sandbox ou conteneur, tokens à portée minimale.
  • Trio létal : données privées + contenu non fiable + capacité d’envoyer vers l’extérieur. Casser un des trois, c’est le rôle de la garde d’action.

L’AI gateway : un seul point de passage

Module 6 · slide « L’AI gateway : un seul point de passage »

Un proxy entre vos agents et les fournisseurs de modèles : une seule API côté agents, N fournisseurs derrière, aucune clé de fournisseur sur les postes.

Fonction Ce qu’elle apporte
Routage choix du modèle, fallback si un fournisseur tombe
FinOps quotas et plafond de dépense par équipe
Observabilité tokens, coût et latence par appel (souvent en OpenTelemetry)
Emballement coupe l’agent coincé dans une boucle
Guardrails masquage, détection d’injection : appliqués à tous
Traçabilité modèles autorisés, résidence des données, audit
  • La gouvernance sans modifier les agents : ajouter un masquage ou changer de fournisseur se fait dans la gateway, une fois.
  • Le plafond de dépense est le garde-fou le plus simple, à poser dans la gateway.
  • Attention au cache sémantique de certaines gateways : il renvoie une réponse déjà générée pour une question « proche ». Utile pour une FAQ, dangereux pour un agent de code. À ne pas confondre avec le prompt caching du fournisseur (module 1), qui ne change pas la réponse.

Le budget caché : au-delà des tokens

Investir ou attendre : le test à trois questions

Module 6 · slide « Investir ou attendre : le test à trois questions »

Question Investir Attendre
Spécifique ? contexte propre à l’équipe ou au produit générique : ce que le modèle fera bientôt nativement
Répété ? plusieurs fois par semaine rare : le geste qu’on fait deux fois par an
Maintenu ? un propriétaire identifié orphelin : personne ne le maintiendra

Trois oui : on écrit la skill ou le hook. Un non : on attend.

  • Le critère du propriétaire est le plus discriminant : une skill non maintenue est pire qu’absente (agentic debt).
  • La seule mesure qui vaut est la vôtre : combien de fois la skill s’est déclenchée, et le temps qu’elle a évité de réexpliquer. Trois skills utilisées valent mieux que vingt dans le dépôt.

Réversibilité : éviter le vendor lock-in

Module 6 · slide « Réversibilité : éviter le vendor lock-in »

Principe Pourquoi
Harness ≠ fournisseur l’adhérence est dans le harness ; les modèles changent tous les trimestres
Modèle via la gateway basculer sans réécrire l’outillage
Formats ouverts AGENTS.md, SKILL.md, MCP survivent à un changement d’outil
Résidence des données à exiger au contrat : aucune donnée ne sert au réentraînement, hébergement connu

Modèle via la gateway : les agents appellent un nom interne (ex. code-standard), la gateway choisit le modèle réel derrière. Changer de modèle devient un réglage côté gateway, à condition que le harness accepte une adresse d’API personnalisée.

Choisir un harness, un modèle, un fournisseur : trois décisions désormais séparables, selon trois postures.

Posture Exemples Ce que ça implique
Mono-fournisseur Claude Code le harness impose la famille de modèles : cohérence maximale, arbitrage impossible ; l’hébergement reste négociable
Catalogue multi-éditeur GitHub Copilot un contrat, plusieurs modèles au choix en session : arbitrage coût / puissance sans changer d’outil
Agnostique OpenCode, Pi, Aider ; Codex par configuration (fournisseurs compatibles API OpenAI, modèles locaux) le fournisseur est un paramètre : liberté totale, intégration (permissions, support) à votre charge

Tip du module : Tracé et portable : un agent qu’on peut auditer, et quitter. Commits tracés, specs versionnées, appels journalisés par la gateway, formats ouverts.

Une requête, de bout en bout

Clôture · slide « Une requête, de bout en bout »

Exemple : « ajoute la pagination par curseur sur GET /bookings, avec ses tests ».

  1. SDD : une tâche issue d’une spec relue.
  2. Orchestrer : la tâche est confiée à un agent.
  3. Harness : construit le contexte, préfixe stable en tête (AGENTS.md, demande initiale).
  4. Gateway : filtre, route et journalise l’appel.
  5. Modèle : prefill en cache, puis decode.
  6. Harness : hook, permission, tool, puis il reboucle.

Le modèle prédit, le harness agit, la gateway gouverne.

Trois idées à garder

Clôture · slide « Trois idées à garder »

Idée En une phrase Le réflexe
1. Le contexte fait la facture l’entrée domine, le préfixe stable est en cache, les sous-agents isolent sans être gratuits mesurer ce qui entre
2. Le harness agit ce qui doit arriver se configure (hook, sandbox, tests), ça ne se demande pas hook plutôt que consigne
3. La gouvernance se trace spec versionnée, commit tracé, appels par la gateway, revue humaine là où ça compte ce qui n’est pas tracé n’est pas gouverné

Pour aller plus loin : « Building effective agents », Anthropic (2024) ; « Attention Is All You Need », Vaswani et al. (2017) ; « Intro to LLMs », Andrej Karpathy ; OWASP Top 10 for LLM (2025).

À retenir

  1. La revue passe du poste à la CI ; la gouvernance des merges suit le risque.
  2. La garde d’action borne le risque, les gardes d’entrée et de sortie le réduisent.
  3. La gateway route, plafonne, observe et trace, pour toute l’entreprise.
  4. Un budget IA compte aussi la CI et le temps de revue ; on investit sur le spécifique, répété, maintenu.

Une phrase par terme : les mêmes mots, avec le même sens, que dans la formation business et la Foundation, puis les termes propres à l’Avancé.

Terme En une phrase
IA générative IA qui produit du contenu (texte, image, code) au lieu de seulement classer ou prédire un chiffre.
LLM (Large Language Model) Modèle entraîné sur d’énormes volumes de texte, qui génère une réponse en prédisant le mot suivant.
Token Morceau de mot traité par le modèle ; c’est aussi l’unité de facturation (≈ ¾ de mot en anglais).
Hallucination Réponse fausse mais présentée avec assurance et vraisemblance.
Knowledge cutoff (date de coupure) Date à laquelle s’arrêtent les données d’entraînement du modèle ; il ignore tout ce qui s’est passé après, sauf s’il fait une recherche web.
Assistant Le produit qu’on utilise au quotidien (ChatGPT, Copilot, Claude.ai, Gemini) : une interface posée sur un harness, autour d’un modèle.
Harness Tout le logiciel autour du modèle : consignes, mémoire, tools, enchaînement des étapes. Deux assistants sur le même modèle diffèrent par leur harness.
Tools Capacités que le modèle peut appeler pendant sa réponse : recherche web, calcul, lecture de fichiers, Jira, Figma… (tool calling).
MCP (Model Context Protocol) Standard pour brancher de nouveaux tools sur un assistant : applications et données de l’entreprise.
Agent Modèle qui enchaîne lui-même des actions avec des tools, en boucle, jusqu’à atteindre un objectif : c’est la boucle agentique (modèle + tools + boucle + objectif, que le harness fait tourner). Les éditeurs utilisent aussi « agent » pour de simples assistants personnalisés.
Boucle agentique (agent loop) Le cycle demande → le modèle choisit un tool → le harness l’exécute → le résultat entre dans le contexte → on recommence si besoin.
Prompt La demande envoyée au modèle, consignes comprises.
Skill Savoir-faire emballé (consignes, modèles, exemples, parfois des scripts) que l’assistant charge à la demande, quand la tâche correspond. Plus léger que des instructions permanentes, partageable dans une équipe. Claude parle d’« Agent Skills » ; d’autres assistants ont des équivalents.
Vibe coding Produire vite un prototype en langage naturel, sans regarder le code ; parfait pour explorer, insuffisant pour livrer.
AI-driven development Développement logiciel où l’IA écrit beaucoup de code, sous la direction et le contrôle d’ingénieurs.

Tronc commun : contexte, risques et coûts (rappel)

Modules 1, 3 et 6

Terme En une phrase
Context window Tout ce que le modèle « voit » au moment de répondre : consignes, historique, pièces jointes, résultats des tools.
Session Une conversation ; elle accumule du contexte, utile ou parasite.
Mémoire Informations que l’assistant réinjecte automatiquement d’une session à l’autre (profil, préférences) ; souvent désactivable.
Grounding Ancrer la réponse dans des sources vérifiables plutôt que dans la « mémoire » du modèle.
RAG (Retrieval-Augmented Generation) Technique de grounding : on cherche les bons extraits de documents internes et on les ajoute au contexte avant de répondre.
Cache Mise en mémoire du début du contexte pour ne pas le repayer plein tarif à chaque message (il est relu à prix réduit) ; changer de modèle ou de tools en cours de route le perd.
Human-in-the-loop Un humain qualifié valide la sortie de l’IA avant qu’elle soit utilisée.
Prompt injection Instructions malveillantes cachées dans un contenu (email, document, page web) qui détournent un assistant.
Fuite de données Données confidentielles envoyées à un assistant non maîtrisé (version grand public).
Plafond de dépense (spend cap) Limite de budget configurée pour éviter les factures surprises.

Rappel de la Foundation

Termes de la Foundation repris dans les modules 1 à 6

Terme En une phrase
Agent de code Agent qui lit, modifie et exécute du code dans un dépôt (Copilot, Claude Code, Codex, Cursor…).
System prompt Consignes que le harness place en tête de chaque appel, avant les instructions projet et la conversation.
Tool definitions Nom, description et paramètres de chaque tool, envoyés au modèle à chaque appel : ils pèsent dans la context window et se lisent comme un prompt.
Instructions projet (AGENTS.md) Fichier versionné dans le dépôt, chargé à chaque session : conventions, commandes, pièges. C’est l’équivalent dev des instructions personnalisées.
Demande initiale Premier message de la session, cadré pour la tâche du jour : objectif, fichiers clés, commandes, invariants, pièges. Pour une tâche longue, on l’écrit dans un fichier rechargé à chaque session.
Invariant Règle qui doit rester vraie quoi que fasse l’agent (un contrat d’API, une règle métier, un test qui doit passer).
Niveau d’autonomie Ce que l’agent peut faire sans demander : proposer, modifier après accord, ou agir seul.
Permissions Les actions autorisées à l’agent (lire, écrire, lancer une commande, accéder au réseau).
Revue IA Relecture d’un diff par un agent ; elle aide l’humain, elle ne décide pas du merge.
Progressive disclosure L’agent ne voit d’abord que le nom et la description d’une skill, et ne charge son contenu que quand il en a besoin.
Context rot (en business : dérive de contexte) Dégradation des réponses quand la context window se remplit d’ajouts, de corrections et d’informations périmées ou contradictoires : la session reste crédible mais s’éloigne du besoin initial.
Compaction Résumé automatique ou demandé de la session pour libérer de la context window.
Lost in the middle Le modèle exploite moins bien ce qui se trouve au milieu d’un long contexte.
Trio létal Données privées + contenu non fiable + capacité d’envoyer vers l’extérieur : la combinaison qui rend une fuite possible.

Termes propres à l’Avancé : sous le capot

Module 1

Terme En une phrase
Prefill / decode Les deux temps d’une réponse : lire tout le contexte, puis générer token par token.
KV cache Mémoire de calcul du modèle qui évite de relire le contexte déjà traité.
Prompt caching Le fournisseur réutilise le début inchangé du contexte d’un appel à l’autre, moins cher et plus rapide.
Reasoning tokens (effort) Tokens de « réflexion » que le modèle génère avant de répondre ; ils améliorent les tâches difficiles et se paient.
SLM Petit modèle, souvent local et spécialisé, moins cher et plus rapide qu’un LLM.

Termes propres à l’Avancé : le harness et le contexte

Modules 2 et 3

Terme En une phrase
Agentic debt Dette créée quand on empile sur son harness des réglages, extensions et contournements qu’on ne maîtrise plus.
Allowlist Liste des commandes que l’agent peut lancer sans demander. Ce n’est pas une sandbox.
Sandbox Environnement isolé qui limite ce que l’agent peut toucher, même si on l’a autorisé.
Hook Action déterministe déclenchée par le harness à un moment précis (avant une commande, après une édition), quoi que dise le modèle.
Sous-agent (subagent) Agent lancé par l’agent principal dans un contexte isolé, qui ne renvoie que son résultat.
Context engineering Choisir ce qui entre dans la context window, quand et sous quelle forme.
Recherche agentique L’agent cherche lui-même dans le code (grep, lecture de fichiers) au lieu de recevoir des extraits préparés.
Embeddings / indexation du code Représentation du code qui permet de retrouver les passages pertinents par le sens ou par la structure.

Termes propres à l’Avancé : spec et qualité

Module 4

Terme En une phrase
SDD (Spec-Driven Development) Développement où la spec versionnée est la source de vérité que l’agent implémente et que les tests vérifient.
Spec-first / spec-anchored / spec-as-source Les trois postures du SDD : la spec sert à démarrer, reste maintenue avec le code, ou devient la seule chose qu’on édite.
Spec-centric / workflow-centric Les deux familles d’outillage du SDD : la référence est la spec versionnée, ou une discipline de travail encodée en skills.
Drift Écart qui s’installe entre la spec et le code.
Tests de construction / tests fonctionnels Tests qui aident l’agent à converger sur l’implémentation, jetables / tests des effets observables, durables : la spec exécutable.
Mutation testing Technique qui modifie le code exprès pour vérifier que les tests détectent le changement.

Termes propres à l’Avancé : orchestrer et gouverner

Modules 5 et 6

Terme En une phrase
Orchestrateur Logiciel ou agent qui répartit le travail entre plusieurs agents et assemble leurs résultats.
Fiabilité composée La fiabilité d’une chaîne d’agents est le produit de celle de chaque étape : 0,95 sur 10 étapes donne environ 60 %.
Worktree (git worktree) Deuxième répertoire de travail rattaché au même dépôt, sur une autre branche : deux agents peuvent travailler en parallèle sans se gêner.
Guardrails Contrôles en entrée, en sortie et sur les actions d’un agent.
Gateway (AI gateway) Point de passage unique entre les agents et les fournisseurs de modèles : routage, coût, traçabilité, règles.
Evals Jeux de tests qui mesurent la qualité des réponses d’un agent ou d’une skill.
Quality gate Contrôle automatique qu’une PR doit passer avant le merge (tests, analyse statique, evals, revue agentique).
Vendor lock-in Dépendance à un fournisseur qui rend coûteux un changement d’outil ou de modèle ; formats ouverts et gateway la réduisent.
